# 高優先度の負荷改善

対象の基準版: `da673b3e571a8f2474bdee281fdbba9fa0149795`。寺院情報の空欄保持に関する直近の変更を引き継いでいます。

## 修正内容

- 自動同期は、最後に送信成功した内容と表ごとに比較し、変更のある表だけを送信します。派生項目、家族、並び順、削除も出力値で比較します。変更対象の表の消去と書き込みは、引き続き1回のatomic batchUpdateで処理します。
- 初回、再読み込み後、取り込み後、送信先変更後、通信結果が不確かな場合は全件から同期します。手動の全件出力・指定表出力は従来通りです。比較用キャッシュは1つの送信先だけをメモリ上に保持し、永続保存しません。
- 古い記録で作成・修正日時が未設定の場合、同期するたびに現在日時を作って書き込む処理をやめました。既存の日時は保持し、不明な部分は空欄にします。テンプレート等の出力時刻の変化だけでは更新対象にしません。
- 同期出力の過去帳と世帯の結び付けを索引化しました。新盆順も世帯別に過去帳をまとめ、各世帯の判定を1回にしてから従来と同じ順で並べます。
- 安全用・取り込み前バックアップの二重保存を解消しました。遠隔取り込み時の大きな6種類の表は同期用メモリを即時更新し、画面の状態に連動する保存処理で1回だけ永続化します。小さい設定のJSON文字列とオブジェクトを二重にIndexedDBへ保存する処理も解消しました。
- 同期中の追加編集が成功後に再評価されるようにしました。最新の同期用状態を使い、空配列になった削除を古い画面の値で置き換えません。

OAuth、Firebase設定、シートの表形式、データ保護の一括更新方式は維持しています。

## 確認

既存10件と追加5件、計15件のテスト、およびTypeScript検査が通過しました。追加テストは、7月盆・8月盆の昇降順の一致、変更のない表の送信省略、家族・世帯主等の派生情報、最終1件の削除、失敗時の再送、取り込み後のキャッシュ破棄、端末内の保存回数、同期中の追加編集を確認します。ビルドはGitHub Actionsでも確認します。

2026年9月11日に1,500世帯・過去帳15,000件の架空データを使い、同じ端末上で直前の版と比較しました。Node.jsで測定し、通信は模擬応答です。実際のGoogleシートには書き込んでいません。

| 項目 | 修正前 | 修正後 |
|---|---:|---:|
| 新盆順の並べ替え | 3,528ms | 301ms |
| 檀家の電話番号1件変更時の最大リクエスト本文 | 約11.23MB（全表） | 約1.44MB（檀家名簿） |
| 会計金額1件変更時の最大リクエスト本文 | 約11.23MB（全表） | 約1.65KB（会計1件の表） |

並べ替えは約11.7倍、電話番号編集の本文は約87%削減でした。会計の例は会計レコードが1件のみのテストであり、実際の会計・操作履歴の件数によって送信量は増えます。数値は圧縮前UTF-8 JSONで、ネットワーク待ち時間は含みません。

変更のない表も比較のために出力値を生成しますが、今回の規模で変更なしの処理は約29ms、Google API呼び出しは0回でした。初回の全件出力は約11.23MBのままです。今回は表単位の差分同期であり、大きな表そのものの行単位同期や、前回の調査で優先度「中」とした画面の遅延読み込み・一覧・地図は対象外です。
